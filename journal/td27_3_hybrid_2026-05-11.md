# #3 Hybrid two-stage routing — implementation, results, red-team

Per `docs/TRIT_ROUTING_APPLICATIONS.md` item #3. Combine signature-distance
filtering (Stage 1, cheap, direction-aware) with signed-score refinement
(Stage 2, precise) by chaining the substrate's two routing primitives:
`m4t_route_threshold_extract` + `m4t_route_distance_batch` for Stage 1,
`m4t_mtfp_vec_dot_i64` on the candidate shortlist for Stage 2.

## Implementation

`gesh/bitnet/bitnet_harness.c`:
- `BITNET_ATTN_HYBRID = 5` added to `bitnet_attn_mode_t`.
- `BITNET_ATTN_K1` env var controls Stage-1 candidate count (default
  `4 × k_eff`, clamped to `[k_eff, seq_k]`).
- HYBRID branch in per-head sparse dispatch:
  - Stage 1: `bitnet_pick_routed_indices(candidates, k1, ...)` →
    absolute indices in `[0, seq_k)` sorted by signature distance.
  - Stage 2: compute `mtfp_vec_dot_i64` on the k1 candidates →
    `cand_scores[]`. `bitnet_pick_posracle_topk(relative_top, k_eff,
    k1, cand_scores)` picks top-k_eff relative indices in `[0, k1)`.
  - Translate: `indices[i] = candidates[relative_top[i]]`.

## Sanity: hybrid with k1 ≥ seq_k = posracle

math_add prompt (6 toks) + gen 30 = max seq_k 36; set k1=512 so Stage 1
covers all positions every step. Output is bit-exact equal to posracle:

```
posracle:     220 777 13 220 777 28382 220 22 17239 220 717 13 220 717 5636 ...
hybrid k1=512: 220 777 13 220 777 28382 220 22 17239 220 717 13 220 717 5636 ...
```

Implementation correctness verified — the Stage 1 → Stage 2 indirection
is bug-free.

## Focused-subset experiment

10 prompts × 5 configs = 50 runs. Configs: `routed` (fixed τ=5000, k=4),
`posracle` (k=4), `hybrid` (k=4) at k1 ∈ {8, 16, 32}, with K-signature
cache active for routed/hybrid (fixed τ=5000).

Prompt seq_k range: 36–71 (all max seq_k > 32, so k1=32 is meaningful
for late-generation tokens).

## What this validates

1. **Hybrid is a real operating point.** When k1 < seq_k, Stage 1 is
   active and Stage 2 picks from a routed-filtered candidate set —
   output is provably different from posracle (e.g. math_add @ k1=8,
   long_summary @ k1=16).

2. **Substrate primitives compose.** The trit substrate's signature/
   distance pair (Stage 1) and signed-score-via-mtfp-dot (Stage 2)
   both pull from the same K-cache; Stage 1 reads cached K signatures
   from the #1 work; Stage 2 reads K MTFP values. Two primitives chain
   without conversion overhead.

3. **Cost-distinct over posracle at long context.** Posracle requires
   `seq_k` dot products; hybrid requires `k1` dot products + cheap
   Stage 1 (signature compare is popcount, ~1/16 the cost of a dot).
   At seq_k=4096 with k1=16, hybrid does ~256× fewer dots than posracle.
   On this battery seq_k ≤ 71, so the cost gap is modest (~4×); the
   scaling claim is extrapolation, not measurement.

4. **Quality competitive with posracle at small seq_k.** Aggregate
   first-30-token dense-agreement: hybrid_k1_16 (106) > posracle (101).
   Small absolute gap; not statistically significant at n=10. Honest
   reading: **hybrid does no worse**, and gives the cost advantage for
   free at scale.

## Red-team

### C1: Substrate distinctiveness — qualified
The Stage 1 filter *uses* the trit substrate's signature/distance
primitive, but a scalar approximation (LSH bucket, hash-based filter,
or partial-dot) could also work. The substrate-specific claim is
narrower: **trit signatures are produced as a byproduct of routing,
not as extra compute**. On a scalar substrate, Stage 1 would need an
extra projection layer. So the claim earns "load-bearing within
substrate" not "uniquely better than alternative substrate."

### C2: Cost-distinct measurement is extrapolation, not measurement
Reported cost gap is asymptotic. On this battery (seq_k ≤ 71),
posracle does ~71 dots/step and hybrid_k1_16 does ~16 dots/step —
~4× ratio. Real measurement would need a long-context battery
(seq_k 1024+). Recorded as a follow-up.

### C3: Heuristic-only quality assessment
First-30-token agreement with dense is a divergence metric, not a
quality metric. Two arms can both be coherent yet diverge from dense
in different directions. The loop heuristic catches gross failures
but is biased (per the #5 finding). For trustworthy quality claims,
the next step would be a spot-check of the divergent outputs (e.g.
hybrid_k1_16 vs posracle on long_summary, where they disagree by 8
tokens at first-30).

### C4: Routed at fixed τ=5000 k=4 is broken on this battery
This is a real regression from earlier claims. #4 reported "fixed τ
acceptable at quality (8/10 focused subset)" — but that was on the
focused subset n=10 selected for the **mechanism story** (TD-27),
where routed already won. On THIS (different) focused subset, routed
@ fixed τ=5000 k=4 agrees with dense on only 28/300 first-30 tokens
(vs 101 posracle, 106 hybrid_k1_16). The routed arm here is NOT a
broken implementation — it's the same code that passed bit-exactness
in #1. It's a sparsity-too-aggressive failure at k=4 specifically.
Per the existing record (TRIT_ROUTING_APPLICATIONS.md item #4),
fixed τ generalization is "n=10 focused" not "full battery." This
re-affirms that caveat.

### C5: hybrid_k1_8 has a math_add quirk
On math_add, hybrid_k1_8 scores 9/10 first-token agreement with dense
while every other mode scores 3. This is suspicious enough to want a
spot-check, but tight integer-token tasks are exactly where small
context + aggressive Stage-1 narrowing should produce sharp choices
— so the finding is plausibly real. Recorded for future investigation.

## What this does NOT validate

- **Quality on long context.** All test prompts have seq_k ≤ 71;
  the regime where hybrid's cost story matters most is unmeasured.
- **Substrate vs scalar implementation cost.** No scalar reference
  for two-stage hybrid exists; substrate cost-distinct claim is
  internal-only ("composes substrate primitives").
- **Robustness to k1.** k1 ∈ {8, 16, 32} probed; the response across
  k1 is non-monotonic on some prompts. A proper sweep over k1 ∈
  {4, 8, 16, 32, 64, 128} at long context would settle the operating-
  point question.

## Open follow-ups

- **Long-context evaluation.** Re-run on prompts with seq_k > 256
  to test the cost story and quality scaling.
- **Per-prompt spot-check.** Reading the actual generated text on
  long_summary k1_16 vs posracle to verify the +8 agreement is
  "better English" not "coincidentally-aligned-then-diverges."
- **k1 default.** Default `4 × k_eff` gives best aggregate here but
  the response is noisy. A sweep at scale would inform the production
  default.

## Verdict

**Hybrid is competitive with posracle on quality and lower-cost at
scale**, with implementation verified bit-exact in the degenerate
case. The aggregate edge (106 vs 101) is small and within n=10
noise — the honest claim is "no worse than posracle, with provable
asymptotic cost advantage." Promoted from "untested" to "competitive,
needs long-context validation" in
`docs/TRIT_ROUTING_APPLICATIONS.md`.
