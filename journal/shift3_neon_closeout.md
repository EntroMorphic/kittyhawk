## Performance summary

```
Workload shape: BATCHED (n=4096, one call, scalar uses sdiv)
  k= 1: scalar 1.06 ns/elem  →  NEON 0.11 ns/elem  =  9.6× speedup
  k= 7: scalar 0.98 ns/elem  →  NEON 0.10 ns/elem  =  9.5× speedup
  k=13: scalar 0.92 ns/elem  →  NEON 0.10 ns/elem  =  9.6× speedup
  k=19: scalar 0.87 ns/elem  →  NEON 0.09 ns/elem  =  9.5× speedup

Workload shape: TIGHT-LOOP (n=4 per call, 200K calls — per-call overhead bound)
  k= 1: scalar 0.93 ns/elem  →  NEON 0.14 ns/elem  =  6.5× speedup
  k= 7: scalar 0.87 ns/elem  →  NEON 0.14 ns/elem  =  6.3× speedup
  k=13: scalar 0.84 ns/elem  →  NEON 0.13 ns/elem  =  6.4× speedup
  k=19: scalar 0.83 ns/elem  →  NEON 0.13 ns/elem  =  6.3× speedup
```

The headline 9.5× (BATCHED) is the regime where shift3 is most useful — bulk divide of an MTFP buffer by a fixed `3^k`. TIGHT-LOOP shape (small per-call batches) still benefits 6–7×.

## What's structurally true now

**The substrate's `m4t_mtfp_shift3` divide direction now runs at NEON throughput on Apple Silicon.** Pre-cycle, the divide direction was scalar `sdiv` + round-to-nearest logic (~5.8 cycles/element). Post-cycle, it's NEON `smlal + sshl + vmovn` (~0.6 cycles/element on the BATCHED workload). The multiply direction (k > 0) is partly auto-vectorized by AppleClang already (per G4 finding) but uses scalar 64-bit muls inside NEON shuffles — further headroom remains there for a future cycle.

**Update (2026-05-04, post-redteam remediation):** the original framing here said "no longer has a slow direction" — too strong, since the multiply direction's auto-vectorization isn't true SIMD multiply. Corrected per `journal/shift3_neon_redteam.md` M4 / `shift3_neon_remediation_*.md` R-G10.

**The magic table is the formal record.** `m4t/src/m4t_pow3_magic.h` is the committed, exhaustively-verified source. Anyone needing to verify the table can re-run `gen_pow3_magic.c` and diff. No surprise drift.

**Bit-exact regression coverage is automated.** `m4t_shift3_neon` ctest entry runs sample-based on every CI build. Exhaustive verification (G1) is on-demand (`./test_m4t_shift3_neon x`) — too slow for ctest but cheap when the magic table changes.

## Honest concerns from this cycle (residual; for future cycles)

**1. The cross-exponent accumulator (`m4t_mtfp_vec_accum_aligning`) doesn't benefit from this kernel.** It does per-cell-varying-k division; this kernel is one-k-per-batch. A vector-of-Ms variant of this technique might apply, but it's a different kernel design and not in this cycle's scope. Documented in SYNTHESIZE as deferred.

**2. The multiply direction (k > 0) is auto-vectorized differently from the divide direction.** The disasm at G4 showed AppleClang vectorizing the multiply path with NEON `dup + sshll + scalar mul + cmgt + bif + uzp1`. The vectorization uses scalar 64-bit multiplies inside NEON shuffling (not true SIMD multiplies). The technique from this cycle could plausibly accelerate the multiply direction further, but no consumer measurement justifies pursuit yet.

**3. The original `vqrdmulh + vrshl` two-stage approach was abandoned.** It might be salvageable via per-k specialization with constant-shift `vrshrq_n_s32`, giving an estimated 1.5–2× over the 64-bit-intermediate path. Not pursued. The 9.5× is enough; chasing 15× before there's a consumer demand is premature.

**4. The G1 exhaustive verify is intentionally NOT in ctest.** 25-second runtime is too long for routine builds. It's available manually via `./test_m4t_shift3_neon x`. If the magic table is ever regenerated, this must be re-run.

**5. `gen_pow3_magic.c` itself is not in ctest, and its output (the header) is not auto-checked against the committed header in CI.** Drift discipline is documentation-level: regenerate, diff, commit. A future cycle could add a CI check that runs the generator and confirms output matches the committed header. Not done here.

## Methodology lifted (lock-in for future cycles)

- **For magic-multiply division: 64-bit intermediate (`vmull + bias + arith-shift`) over 32-bit-with-rounding (`vqrdmulh + vrshl`).** The latter has compound rounding error that's hard to make bit-exact across all magnitudes; the former is one rounding step end-to-end. Trades ~1.5× perf for bit-exactness simplicity.

- **Always exhaustively verify the NEON kernel against the scalar reference, not just the emulator.** The emulator is one bridge; the NEON intrinsics are another bridge. Both must match. Do exhaustive at table-generation time AND on the kernel itself.

- **`vmovn_s64` narrowing requires a written saturation argument, not just empirical observation.** The compiler doesn't insert saturation; if the int64 value exceeds int32, you get garbage. Bound the worst case explicitly.

- **Workload-shape-explicit bench is non-negotiable for kernel speedup claims.** Per CONTRIBUTING.md scope-match rule (added in concern #4). Single-shape numbers under-determine the conclusion.

- **G7 source-of-truth pattern.** Generated constants live in committed headers, regenerable via committed tools. No copies in test source. Drift is impossible if the pattern is followed.
